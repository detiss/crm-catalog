2. ОБРАНА ТЕМА: СЕГМЕНТИ, ТЕГИ ТА ФІЛЬТРИ (БЛОКИ-ПЛАШКИ)
--------------------------------------------------------

2.1. Що це

  - 7 сегментів «Для кого»: E-commerce, Малий бізнес, Середній бізнес, Enterprise,
    B2B-продажі, Сервісні центри, Команди та проєкти.
  - 11 тегів «Можливості»: Безкоштовний тариф, Мобільний застосунок, Маркетплейси,
    Нова Пошта, Месенджери в одному вікні, Управління проєктами, Фінанси та склад,
    Відкритий код, Low-code, Gmail / Google, IP-телефонія.
  - Окремий фільтр «Тип рішення» (хмара / коробка).
  - Плашки в рядку таблиці: перша (темна) показує, для кого CRM, далі йдуть її теги.

Ці критерії дозволяють відвідувачу швидко знайти CRM під свої потреби, як у каталозі
E-Katalog, але без бази даних.

2.2. Де це реалізовано

  src/data/crms.ts
      Списки SEGMENTS і FEATURE_TAGS (єдине джерело), тип Crm (поля segments та tags)
      і дані всіх 10 CRM.
  src/sections/FilterPanel.tsx
      Ліва панель: чекбокси створюються циклом по SEGMENTS і FEATURE_TAGS.
  src/pages/Home.tsx
      Стан вибраних фільтрів і сама фільтрація.
  src/sections/CrmTable.tsx
      Плашки в рядку таблиці (до 4 тегів на CRM).
  src/sections/AddCrmDialog.tsx
      Форма «Додати CRM»: ті самі списки як кнопки вибору.
  src/data/crms.en.ts
      Англійські назви сегментів і тегів (SEGMENT_EN, TAG_EN).
  src/i18n/
      Підстановка перекладів при показі.

2.3. Як це працює

Дані одного запису (src/data/crms.ts):

    {
      id: 'keepincrm',
      segments: ['Малий бізнес'],
      tags: ['Безкоштовний тариф', 'Маркетплейси', 'Нова Пошта'],
      ...
    }

Фільтрація (src/pages/Home.tsx):

    if (segSel.size > 0 && !c.segments.some((s) => segSel.has(s))) return false;
    if (tagSel.size > 0 && !c.tags.some((t) => tagSel.has(t))) return false;

Правила:
  - Вибрані значення зберігаються в Set (множина), кожен клік додає або прибирає
    значення.
  - Усередині однієї групи діє «АБО»: підходить CRM, яка має хоча б один вибраний
    сегмент або тег.
  - Між групами (сегмент, тип рішення, теги, пошук) діє «І»: фільтри звужують список.
  - Порожній вибір означає, що фільтр вимкнено. Є лічильник «Фільтри (N)» і кнопка
    «Скинути».

Потік даних:

    crms.ts (SEGMENTS, FEATURE_TAGS, CRMS)
        |-> FilterPanel   (що показати в панелі)
        |-> Home          (які CRM залишити в списку)
        |-> CrmTable      (які плашки намалювати)
        |-> AddCrmDialog  (з чого користувач обирає критерії для своєї CRM)
        '-> crms.en.ts    (як підписати ці критерії англійською)

2.4. Чому саме так, а не інакше

  1) Немає бекенду. GitHub Pages віддає лише статичні файли, а в першому промпті
     вимога була «мінімальний бек». Тому дані лежать у TypeScript-файлі, який
     вбудовується в сайт під час збірки.

  2) Один список для трьох місць. Панель фільтрів, плашки та форма додавання беруть
     критерії з одного списку. Новий тег з'являється у фільтрі та у формі автоматично,
     нічого не треба правити в кількох файлах.

  3) TypeScript перевіряє дані під час збірки. Якщо в записі бракує поля або
     priceLevel вказано неприпустимий (допустимі лише 1, 2, 3), збірка падає, GitHub
     Actions показує червоний хрестик, а на сайті лишається остання робоча версія.
     Це підтвердилося на практиці: коли блок CRM вставили не туди, збірка впала, але
     сайт не зламався.

  4) Прості рядки замість числових ідентифікаторів. У файлі даних усе читається
     очима, змінити його може людина без досвіду програмування, а фільтр зводиться до
     звичайного порівняння рядків.

  5) Мова окремо від даних. Ключі лишилися українськими, а англійські назви лежать у
     словниках SEGMENT_EN та TAG_EN і підставляються лише при показі. Тому фільтри не
     ламаються при зміні мови.

Чому не база даних або сервіс на кшталт Firebase: для 10 записів це зайвий сервер,
ключі та акаунти, а сайт перестав би бути простою статичною сторінкою. Чому не окремі
JSON-файли на кожну CRM: це зручно при сотнях записів, а для десяти зайве, і TypeScript
дає перевірку типів, якої в JSON немає.

2.5. Чим це зручно на практиці

  Додати новий тег:
    1. дописати рядок у FEATURE_TAGS (src/data/crms.ts);
    2. дописати його в поле tags потрібних CRM;
    3. за бажанням додати англійську назву в TAG_EN (src/data/crms.en.ts).
  Фільтр і форма додавання оновляться самі.

  Додати нову CRM: один об'єкт у масив. Відвідувач може заповнити форму на сайті, і
  заготовка для вставки в src/data/community.ts потрапляє до автора через Issues.

2.6. Обмеження (чесно)

  - Поля segments і tags мають тип string[], а не «лише значення зі списку». Помилка
    в написанні тегу в crms.ts не зупинить збірку: такий тег покажеться в рядку, але
    за ним не можна буде фільтрувати. Це можна посилити типом
    (typeof FEATURE_TAGS)[number][].
  - Теги працюють як «АБО»: вибір двох тегів показує CRM, що має хоча б один із них.
    Якщо потрібно «І» (усі вибрані), у Home.tsx достатньо замінити some на every.
  - У рядку таблиці видно не більше 4 тегів, але фільтри враховують усі.
  - Першу (темну) плашку дає проста обробка тексту поля bestFor: до першої коми,
    двокрапки або дужки. Окремого поля для неї немає.
  - Вільний текст CRM, доданих відвідувачами, не перекладається автоматично.


3. ІНША РУТИННА РОБОТА, ЯКУ ВИКОНАВ ШІ

Це те, що вручну довелося б збирати й набирати годинами:

  - Темна тема: підбір кольорів і перевірка, що все читається (src/index.css).
  - Документація: GLOSSARY.md (пояснення термінів), STRUCTURE.txt (призначення
    кожного файлу), README.md, цей файл.
  - Автоматична публікація: .github/workflows/deploy.yml (збірка й розгортання на
    GitHub Pages після кожного push).
  - Захист від помилок у формі: перевірка дублів за назвою та сайтом, перевірка
    посилань, обмеження довжини полів, відкидання пошкоджених записів з локального
    сховища браузера.
  - Перевірка роботи: ШІ запускав npm run build та автоматичний тест у браузері
    (63 перевірки: фільтри, пошук, порівняння, форма, збереження мови). Скрипти цих
    тестів у репозиторій не додавалися.
